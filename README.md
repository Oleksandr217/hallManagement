# hallManagement

API для управління конференц-залами, бронюваннями та розрахунком вартості оренди.
Реалізовано як тестове завдання (Backend ТЗ).

## Бізнес-завдання

Компанія здає в оренду конференц-зали. Клієнтам потрібно:

1. Шукати вільні зали за датою, часом і місткістю.
2. Бронювати зал з обраними додатковими послугами (проєктор, Wi-Fi, звук).
3. Отримувати коректний розрахунок вартості, який враховує тарифні пояси доби
   (ранкова знижка, вечірня знижка, пікова націнка).

Адміністраторам потрібно:

1. Керувати каталогом залів (додавання/редагування/видалення).
2. Бачити аналітику — завантаженість залів, дохід, популярність послуг —
   щоб приймати рішення про ціноутворення та розширення парку залів.

## Технічний стек

- **.NET 9**, ASP.NET Core Web API
- **EF Core** + **PostgreSQL** (`Npgsql.EntityFrameworkCore.PostgreSQL`)
- **Swagger / Swashbuckle** — документація API
- **xUnit** — юніт-тести
- **Docker / Docker Compose** — локальний запуск без ручного встановлення .NET SDK чи Postgres

## Швидкий запуск (Docker) — рекомендований спосіб

Потрібен лише встановлений Docker.

```bash
git clone <URL-репозиторію>
cd <назва-папки-репозиторію>
docker compose up --build
```

Дочекайся рядка `Application started. Press Ctrl+C to shut down.` у логах `api`. Після цього:

- **Swagger UI:** http://localhost:8080/swagger

При першому старті контейнер `api` автоматично:

1. застосовує всі EF Core Migrations до бази (`db.Database.Migrate()`);
2. заповнює її початковими даними з ТЗ (Зал А/B/C, послуги Проєктор/Wi-Fi/Звук) через `DbSeeder`.

**Зупинити:**

```bash
docker compose down
```

**Зупинити й видалити дані БД** (для повністю чистого рестарту):

```bash
docker compose down -v
```

## Запуск без Docker (локально)

Потрібен **.NET 9 SDK** і піднятий Postgres.

```bash
# Postgres через Docker (лише база, без API)
docker run --name conference-booking-db \
  -e POSTGRES_USER=postgres \
  -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=conference_booking \
  -p 5432:5432 -d postgres:16

cd src
dotnet restore
dotnet run
```

Рядок підключення береться з `appsettings.json` (`ConnectionStrings:Default`), за замовчуванням очікує Postgres на `localhost:5432`.

## Архітектура

Проєкт побудований за принципами Clean Code — з розділенням на шари за відповідальністю в межах одного проєкту

**Ключові архітектурні рішення:**

- **Інтерфейси репозиторіїв і сервісів** (`Interfaces/`) — бізнес-логіка (`Services/`) залежить від абстракцій, а не від EF Core напряму, що спрощує тестування й заміну сховища даних.
- **`PricingService` винесений окремо від `BookingService`** — правила ціноутворення змінюються незалежно від логіки самого бронювання (Single Responsibility).
- **DTO замість передачі Domain-сутностей назовні** — API не "протікає" деталями схеми БД клієнтам.
- **Сутність послуги названа `Amenity`, а не `Service`** — щоб уникнути плутанини з поняттям "сервіс" (application service, DI) у коді.

## Розрахунок вартості оренди

Найважливіший нюанс ТЗ: бронювання може перетинати кілька тарифних поясів
(наприклад, 08:00–15:00 зачіпає ранкову знижку, стандарт і пік одночасно).

`PricingService` розбиває інтервал бронювання на сегменти за межами тарифних поясів
і рахує кожен сегмент окремо за своєю ставкою, після чого підсумовує:

| Пояс     | Час         | Модифікатор   |
| -------- | ----------- | ------------- |
| Ранковий | 06:00–09:00 | −10%          |
| Стандарт | 09:00–12:00 | базова ставка |
| Піковий  | 12:00–14:00 | +15%          |
| Стандарт | 14:00–18:00 | базова ставка |
| Вечірній | 18:00–23:00 | −20%          |

Приклад: Зал C (1500 грн/год), бронювання 08:00–15:00 →
1×1500×0.9 + 3×1500×1.0 + 2×1500×1.15 + 1×1500×1.0 = **10 800 грн** (+ вартість обраних послуг).

Відповідь `POST /api/Bookings` містить повну розбивку (`pricingBreakdown`) —
клієнт бачить, за що саме платить, а не тільки фінальну суму.

**Прийняте припущення:** вартість додаткових послуг (проєктор, Wi-Fi, звук) — фіксована
за бронювання, не залежить від тривалості. Ціна послуги на момент бронювання
"заморожується" (`BookingAmenity.PriceAtBooking`), щоб майбутня зміна прайсу не змінювала
вартість уже здійснених бронювань.

Бронювання поза межами 06:00–23:00 або таке, що перетинає межу доби, відхиляється
з `400 Bad Request`.

## API Endpoints

### Halls

| Метод    | Шлях                   | Опис                                         |
| -------- | ---------------------- | -------------------------------------------- |
| `GET`    | `/api/Halls`           | Список усіх залів (не видалених)             |
| `POST`   | `/api/Halls`           | Створити зал                                 |
| `GET`    | `/api/Halls/{id}`      | Деталі залу                                  |
| `PUT`    | `/api/Halls/{id}`      | Редагувати зал (часткове оновлення)          |
| `DELETE` | `/api/Halls/{id}`      | Видалити зал (soft delete)                   |
| `GET`    | `/api/Halls/available` | Пошук вільних залів за датою/часом/місткістю |

### Bookings

| Метод  | Шлях                        | Опис                                   |
| ------ | --------------------------- | -------------------------------------- |
| `POST` | `/api/Bookings`             | Забронювати зал з розрахунком вартості |
| `GET`  | `/api/Bookings/{id}`        | Деталі бронювання                      |
| `POST` | `/api/Bookings/{id}/cancel` | Скасувати бронювання                   |

### Reports (аналітика для бізнесу)

| Метод | Шлях                                 | Опис                                   |
| ----- | ------------------------------------ | -------------------------------------- |
| `GET` | `/api/reports/hall-occupancy`        | Завантаженість і дохід по кожному залу |
| `GET` | `/api/reports/revenue`               | Дохід по днях                          |
| `GET` | `/api/reports/popular-services`      | Популярність додаткових послуг         |
| `GET` | `/api/reports/average-booking-value` | Середній чек бронювання                |

Усі звіти приймають опційні query-параметри `from`/`to` (за замовчуванням — останні 30 днів)
і рахують лише підтверджені (`Confirmed`) бронювання — скасовані не враховуються.

Повна інтерактивна документація — Swagger UI за `/swagger`.

## Безпека та відмовостійкість

- **Захист від подвійного бронювання**: перед створенням бронювання перевіряється
  перетин з активними бронюваннями того ж залу. Для повного захисту від гонки умов під високим навантаженням у продакшн-версії
  варто додати `EXCLUDE`-констрейнт Postgres на `(HallId, tstzrange(StartTime, EndTime))`
  через розширення `btree_gist`.
- **Soft delete** для залів і послуг — історія бронювань і звіти лишаються коректними
  навіть після "видалення"; видалення заблоковано, якщо є активні майбутні бронювання.
- **Централізована обробка помилок** — клієнт не бачить stack trace, лише читабельне
  повідомлення й коректний HTTP-код (`400`/`404`/`409`).
- **Валідація вхідних даних** на рівні сервісного шару.
- **"Заморожена" ціна послуг** на момент бронювання — цілісність фінансових даних.
- Непривілейований користувач у Docker-контейнері (`appuser`), а не root.

## Тести

```bash
cd src
dotnet test
```

Покриті юніт-тестами всі сценарії `PricingService`: стандартні/ранкові/вечірні/пікові
години, бронювання, що перетинає кілька поясів, і валідаційні помилки (некоректний

## Міграції

Застосовуються автоматично при старті (`db.Database.Migrate()` у `Program.cs`).

Створити нову міграцію після зміни моделі:

```bash
cd src
dotnet ef migrations add <НазваМіграції>
dotnet ef database update
```
